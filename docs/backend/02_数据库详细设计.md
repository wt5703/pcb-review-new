# PCB 评审平台数据库详细设计

## 1. 约定

- 推荐 MySQL 8，字符集 `utf8mb4`，引擎 InnoDB；最终数据库类型以部署环境确认结果为准。
- 主键使用 `bigint` 或 UUID，项目内统一一种策略。所有时间使用 `datetime(3)` UTC。
- 业务表统一包含 `id`、`created_at`、`created_by`、`updated_at`、`updated_by`、`version`；需要逻辑删除的表增加 `deleted`。
- 枚举保存稳定代码值，不保存中文显示名称。全部 DDL 使用 Flyway 版本化脚本。

## 2. 核心表

| 表名 | 用途 | 关键字段/约束 |
| --- | --- | --- |
| `review_task` | 评审任务 | `task_no` 唯一、`review_type`、`status`、`designer_id`、`project_name`、`design_name`、`pcb_type`、`expected_finish_at` |
| `task_reviewer` | 任务与评审人员处理关系 | `task_id`、`review_role`、`reviewer_id`、`process_status`、`assigned_by`、`assigned_at`、`submitted_at`；唯一 `(task_id, review_role, reviewer_id, deleted)` |
| `review_opinion` | 统一评审意见 | `task_id`、`source_type`、`source_item_id`、`severity`、`content`、`status`、`raised_by`、`raised_at`、`file_version_id` |
| `opinion_reply` | 意见答复历史 | `opinion_id`、`reply_type`、`reason`、`file_version_id`、`replied_by`、`replied_at`、`reply_no` |
| `opinion_confirmation` | 意见确认历史 | `opinion_id`、`reply_id`、`result`、`comment`、`confirmed_by`、`confirmed_at` |
| `task_file` | 任务内业务文件/版本链 | `task_id`、`business_key`、`file_category`、`version_no`、`storage_file_id`、`md5`、`is_latest`、`uploaded_by` |
| `review_check_item` | 任务内互检检查项 | `task_id`、`template_item_key`、`parent_item_key`、`item_name`、`result`、`comment`、`status` |
| `check_item_attachment` | 检查项图片/附件 | `check_item_id`、`file_id`、`sort_no` |
| `opinion_attachment` | 意见图片/附件 | `opinion_id`、`file_id`、`sort_no` |
| `task_flow_record` | 流程流转记录 | `task_id`、`from_status`、`to_status`、`action`、`operator_id`、`comment` |
| `audit_log` | 操作审计 | `trace_id`、`operator_id`、`action`、`object_type`、`object_id`、`result`、`before_json`、`after_json` |
| `outbox_event` | 可靠业务事件 | `event_id` 唯一、`event_type`、`aggregate_id`、`payload_json`、`status`、`retry_count`、`next_retry_at` |
| `notification_record` | 邮件发送记录 | `event_id`、`template_code`、`recipient_hash`、`status`、`provider_message_id`、`failure_reason` |
| `task_archive_snapshot` | 已结束任务归档 | `task_id` 唯一、`snapshot_json`、`archived_at`、`archived_by` |

用户、角色、组织信息优先来自公司身份系统；当前本地联调建立 `user_account`、`role_definition`、`user_role` 三张基础表，分别保存账号、角色定义和用户角色多对多关系。生产环境可由公司身份系统同步这三张表或替换身份适配器，不重复维护密码、令牌等认证凭据。

## 3. 关系与完整性

```text
review_task 1 ── * task_reviewer
review_task 1 ── * review_opinion 1 ── * opinion_reply 1 ── * opinion_confirmation
review_task 1 ── * task_file
review_task 1 ── * review_check_item
review_check_item 0..1 ── 1 review_opinion
review_task 1 ── * task_flow_record / audit_log / outbox_event
review_task 1 ── 0..1 task_archive_snapshot
```

- `review_opinion.raised_by` 与确认人之间的关系由业务校验保证；确认操作必须验证当前用户是该意见提出人。
- `task_file` 对同一 `(task_id, business_key, file_category)` 至多一个 `is_latest=1`。使用事务和唯一约束/部分唯一索引保证。
- 任务结束后禁止新增或更新业务事实；数据库层可通过服务层校验，必要时增加触发器/只读策略作为防御。
- 不建议对核心业务表直接做级联物理删除；保留审计和归档可追溯性。

## 4. 枚举建议

| 枚举 | 示例代码值 |
| --- | --- |
| `review_type` | `PCB`、`SCHEMATIC` |
| `task_status` | 仅使用 PRD 已定义的 PCB/原理图状态代码 |
| `review_role` | `PCB_EXPERT`、`HARDWARE_EXPERT`、`EMC_EXPERT`、`PROCESS_EXPERT`、`STRUCTURE_EXPERT`、`MUTUAL_CHECK` |
| `process_status` | `PENDING`、`IN_PROGRESS`、`SUBMITTED`、`COMPLETED` |
| `opinion_status` | `PENDING_REPLY`、`PENDING_CONFIRMATION`、`CONFIRMED_PASS`、`CONFIRMED_REJECTED`、`WITHDRAWN` |
| `reply_type` | `ACCEPT`、`ACCEPT_NO_CHANGE`、`REJECT` |
| `check_result` | `PASS`、`FAIL`、`NOT_APPLICABLE` |
| `outbox_status` | `PENDING`、`PROCESSING`、`SENT`、`FAILED` |

## 5. 索引与查询

- `review_task(task_no)` 唯一；任务列表索引建议覆盖 `status`、`review_type`、`designer_id`、`created_at`。
- 为项目名称、任务名称、设计者名称的模糊查询选择合适方案：小规模使用前缀索引/LIKE；全文模糊需求另行确认检索方案。
- `task_reviewer(reviewer_id, process_status, task_id)` 支撑“我的任务”。
- `review_opinion(task_id, status, severity, raised_by)` 支撑意见看板和列表筛选。
- `outbox_event(status, next_retry_at)` 支撑定时扫描；`notification_record(event_id, template_code, recipient_hash)` 唯一化防重。
- JSON 快照和审计前后值不作为常规筛选字段；需查询的业务字段应结构化存储。

## 6. 迁移与数据保护

1. 一次需求只新增一个或少量顺序迁移脚本，命名如 `V001__init_task_tables.sql`。
2. 已执行迁移不可修改；需要修正时增加新迁移。
3. 大表变更需采用可在线执行的策略，避免长事务锁表。
4. 迁移必须在测试库执行升级与回归；生产执行前备份和回滚方案由发布流程确认。
