# PCB 评审平台 AI 编码任务拆分

## 任务拆分原则

每个任务按一个业务垂直域交付：领域规则、数据库迁移、应用服务、REST 接口、权限校验、审计/事件影响和自动化测试同时完成。后续任务只能依赖已完成任务公开的接口与数据模型。

## 已实施任务记录

### 本轮需求补充（2026-09-18）

- 根包及 Maven GroupId 已由 `com.leapmotor.pcbreview` 迁移为 `com.bms`；生产代码、测试、日志配置和后端架构文档已同步。
- `POST /check-item-templates/import` 已支持 `multipart/form-data` 的 Excel 批量导入。首个工作表表头必须依次包含（顺序可调整）`评审类型`、`检查项编码`、`父级检查项编码`、`检查项名称`、`排序号`、`是否启用`；评审类型支持 `PCB`/`SCHEMATIC`，启用值支持 是/否、true/false 或 1/0。任何行校验失败会使整份导入回滚。
- `GET /tasks/{taskId}/opinions` 的每条意见返回 `replies` 历史数组：每一项包含答复轮次、答复结论、答复内容、答复人、答复时间，并内嵌该轮唯一对应的 `confirmation`（确认结论、意见、确认人、确认时间；尚未确认时为 `null`）。不再仅返回最新答复的扁平字段，前端可完整回显多轮答复与确认历史。

### 专家意见图片与接口语义收敛（2026-09-20，后续方案已替换）

- 旧版 `opinion_attachment`、`OPINION_ATTACHMENT` 及 `attachmentFileIds` 方案已废弃；专家意见和互检单截图统一随 `richText` 字符串传递和回显，不再建立图片附件关联。
- 设计者答复接口统一为 `POST /opinions/{opinionId}/reply`，专家确认接口统一为 `POST /opinions/{opinionId}/confirm`；旧的复数路径保留兼容，避免已发布前端或集成方立即失效。
- 任务详情“专家意见”页支持直接粘贴截图并写入富文本，不提供图片文件登记或下载入口。

### PCB 流程工作台视觉重构（进行中，2026-09-20）

- 后端现有 PCB 状态机将工艺/结构评审合并为 `PCB_OPTIONAL_REVIEWING`，且未区分三次设计者答复及工艺/结构图上传节点；后续需新增细粒度状态及对应阶段推进动作，前端不能仅靠页签伪造这些业务节点。

### 原理图评审流程工作台适配（进行中，2026-09-20）

- 已将原理图任务详情切换为独立的八步流程：创建、互检分配、互检、设计者答复、硬件专家分配、原理图评审、设计者答复、结束；阶段页签与用户提供的原型一一对应，并保留独立的归档记录页。
- 互检负责人分配会使用 `SCHEMATIC_MUTUAL_CHECK`，硬件专家分配会使用 `SCHEMATIC_HARDWARE_EXPERT`；人员分配成功后，前端调用既有流程接口分别执行 `START_SCHEMATIC_MUTUAL_REVIEW` 或 `START_SCHEMATIC_EXPERT_REVIEW`，不再只是保存人员而没有进入下一阶段。PCB 互检分配同步改为 `PCB_MUTUAL_CHECK` + `START_PCB_MUTUAL_REVIEW`。
- 已新增结束确认检查清单和“确认任务结束”入口，调用既有 `FINISH` 流程动作；后端仍负责校验任务必须已进入结束确认状态、所有处理人已完成、意见已闭环、存在最新设计文件，并在成功后冻结归档。
- 接口复核结论：任务详情使用 `GET /tasks/{taskId}`，人员选择使用当前阶段可分配人员接口，批量互检、意见/答复/确认、流程流转、文件下载和归档接口共同覆盖原型所需的读写数据。原理图状态机目前没有将两次“设计者答复”单独持久化为任务状态，而是通过意见的 `PENDING_REPLY`/`PENDING_CONFIRMATION` 生命周期驱动；页面已按阶段展示。若后续要求这些节点必须作为不可跳过的独立工作流关口，需另行扩展 `TaskStatus` 与流程动作，并补充状态迁移测试。

### 工作台、任务列表与互检单管理页面适配（进行中，2026-09-20）

- 工作台改为统计卡、待处理任务表与流程提醒卡；任务列表和“我的任务”统一任务名称、项目名称、类型、状态、期望完成日期、设计者、评审角色和操作字段的呈现，继续调用既有任务查询与待办接口。
- 创建评审任务页面保持现有字段校验边界和文件多选逻辑，改为从 Mock 用户目录选择设计者、专家/组长；文件由浏览器直接上传公司资源服务，提交仍传用户 ID、冗余姓名及资源服务返回的唯一文件标识，避免页面展示名与服务端权限标识混淆。
- 为支持互检单管理页的真实类别树与操作，`GET /check-item-templates?reviewType=PCB|SCHEMATIC` 返回 `[{ category, items }]`：大类和子项均只含 `id`、`itemName`、`sortNo`，不含 `opinion`、评审类型、内部编码、父级编码、启用状态或版本。删除使用 `DELETE /check-item-templates/<checkItemId>?category=CATEGORY|ITEM`，必须显式声明目标为大类还是小类。大类删除会逻辑停用本评审类型下的全部子项，子项删除只停用该项；类别与记录层级不一致会被拒绝。前端已支持类别树展示、Excel 导入、创建、一次编辑类别及多个子项、逻辑停用。
- 根据互检单管理原型进一步调整：新增类别区固定在页面顶部，直接填写“类别 + 多个检查项”，仅展示业务名称；内部唯一编码在新增时自动生成。下方模板区使用类别卡片、序号、检查项、编辑类别/检查项和删除入口布局；删除按钮仍调用逻辑停用，避免界面文案造成物理删除误解。
- 检查项小类名称编辑收敛为 `PUT /check-item-templates/items/{checkItemId}`：路径仅传检查项 ID，请求体仅传 `itemName`；不要求类别、大类 ID、排序号、内部编码或版本字段。类别编辑仍使用原类别维护接口。
- 修改类别及子项使用 `PUT /check-item-templates`，不再传 `templateId` 或 `reviewType`。`UpdateTemplateRequest` 仅接收 `categoryId`、类别名称和子项列表；子项只传已有项 `itemId`（新增项不传）与 `itemName`。后端根据 `categoryId` 读取类别所属流程，不接收类别或子项的 `enabled`、`version`，并读取保留已有启停状态和版本控制字段。
- 新增检查大项 `POST /check-item-templates` 的 `categoryName` 为必填，`items` 为非必填；可省略或传空数组，后端会只创建大项，后续可再新增对应子项。

### 评审人员白名单（2026-09-22）

- 新增 `POST /reviewer-whitelists`，请求体通过 `roleEmployeeNos` 传递评审角色及多个 `employeeNos`。仅允许硬件（`HARDWARE_EXPERT`）、EMC（`EMC_EXPERT`）、结构（`STRUCTURE_EXPERT`）、工艺（`PROCESS_EXPERT`）和 PCB（`PCB_EXPERT`）评审角色；同一角色不得在请求中重复，单个角色下工号不得重复。前端统一读取 `GET /dictionaries/task-options` 的 `reviewerWhitelistRoles`，获得稳定枚举编码及中文名称。
- 新增 `DELETE /reviewer-whitelists?id={id}` 或 `DELETE /reviewer-whitelists?employeeNo={employeeNo}` 逻辑删除白名单：两者必须二选一；按主键仅删除该条角色—工号映射，按员工工号删除该工号全部启用映射。记录不物理删除，后续新增相同角色和工号时会恢复。
- 任务互检单实例 `task_check_item` 不再保存 `templateItemKey`、`parentItemKey`，改用 `parentId` 表达实例父子关系；查询接口按模板物化类别和子检查项，并在每个检查项的 `opinions` 字段返回该检查项关联的互检意见。
- `reviewer_whitelist` 以一行一个“评审角色 + 员工工号”映射保存，唯一约束保证同一映射不会重复落库。接口重复提交既有映射时幂等忽略，并返回本次新增数量及当前白名单映射。

### 创建/保存任务与评审文件引用一体化提交（已完成，2026-09-21）

- `POST /tasks/save` 和 `POST /tasks/submit` 使用 JSON 任务表单；`files` 为多个已上传文件 UUID 的字符串数组。后端从临时上传记录读取文件名、大小、格式、MD5 和资源路径，不接收前端文件元数据或 `businessFileKey`；同一任务重复传入已关联 UUID 会被拒绝。

- 保存和提交均使用 `application/json`：完整任务 JSON 中的 `files` 仅携带公司资源服务上传后的 UUID 字符串数组，后端从 `pending_file_upload` 读取文件元数据，不接受 `businessFileKey`。新建草稿时 `POST /tasks/save` 不传 `taskId`；编辑草稿时通过 `POST /tasks/save?taskId={taskId}` 指定目标任务，JSON 不携带 `id`。PCB 后端不接收初始文件二进制、不新增初始文件上传接口，也不使用任务乐观锁版本号。
- 工艺、结构等已进入流程后的阶段文件上传仍属于文件模块，不属于任务创建/保存接口。

### 专家意见富文本存储（2026-09-21）

- 专家提出意见时，前端仅提交一个富文本 `content` 字符串（正文及粘贴的截图内容均包含在该字符串中）和问题等级、页面自动判定的意见来源等业务字段。
- 删除 `imageUrl`、`pastedImages` 和 `attachmentFileIds` 的意见接口参数及响应字段；后端不再将专家截图上传资源服务或创建意见附件关联。
- Flyway V15 将 `review_opinion.content` 调整为 `LONGTEXT`，以容纳包含截图的富文本字符串，并移除已废弃的 `image_url` 列；全量 DDL 已同步为最终结构。

### 流程入口统一编排（2026-09-22）

- 已移除 `ReviewerAssignmentController`，不再提供独立的评审人员分配 HTTP 入口。`ReviewerAssignmentService` 保留为流程域内部能力，负责人员关系、权限与多人完成状态校验。
- `POST /tasks/{taskId}/workflow/transitions` 按业务动作拆分参数处理：创建任务固定使用 `POST /tasks/save` 或 `/tasks/submit`，互检单/原理图文件二进制固定使用 `POST /files/upload`；流程接口只负责已创建任务的状态推进。分配互检组员、分配原理图专家、设计者带工艺/结构文件开启评审、管理员结束，以及不附加人员或文件的常规节点推进，分别由控制器的独立处理分支转换为应用层命令，避免一个请求混用不相干参数。
- PCB 组长通过 `START_PCB_MUTUAL_REVIEW + assignedRole=PCB_MUTUAL_CHECK + reviewerIds` 分配互检组员并开始互检；原理图组长通过 `START_SCHEMATIC_MUTUAL_REVIEW + assignedRole=SCHEMATIC_MUTUAL_CHECK + reviewerIds` 分配互检组员；硬件开发部经理通过 `START_SCHEMATIC_EXPERT_REVIEW + assignedRole=SCHEMATIC_HARDWARE_EXPERT/SCHEMATIC_OTHER_EXPERT + reviewerIds` 分配专家并开启原理图评审。
- 设计者可在 `START_PCB_OPTIONAL_REVIEW` 请求中携带 `PROCESS_REVIEW` 阶段文件引用，后端登记后校验前序意见已全部确认通过，再开启工艺/结构评审；`FINISH` 则无需附带人员或文件，直接执行结束确认权限与完成条件校验。
- 验证覆盖：统一流程接口的 PCB 互检多人分配、无意见提交、受限查询，以及“登记公司工艺图并启动工艺/结构评审”的同事务 REST 场景。

### 当前阶段可分配人员与任务详情接口（2026-09-22）

- 已移除 `GET /tasks/{taskId}/workflow/reviewers`。该接口仅返回既有分配记录，无法满足分配页按当前节点筛选候选人的需求。
- 新增 `GET /tasks/{taskId}/workflow/assignable-reviewers`：流程域依据任务当前状态返回可执行分配的 `reviewRole`，白名单域以对应白名单角色关联启用的 `user_account`，返回可直接提交到 `reviewerIds` 的 `userId`、员工工号、姓名和部门。PCB 互检使用 PCB 白名单；原理图互检使用各专业白名单；原理图专家分配分别返回硬件专家及其他专业专家候选组。非人员分配节点会拒绝查询。
- 新增 `GET /tasks/{taskId}`，通过既有任务可见性规则返回单条 `TaskView`；前端任务详情页改为调用此接口，同时候选人员选择器改为使用当前阶段可分配人员接口，而非读取全部 Mock 用户。

### 任务状态字典（2026-09-23）

- 统一字典接口 `GET /dictionaries/task-options` 的 `taskStatuses` 字段返回全部 `TaskStatus` 枚举及中文名称，供任务列表状态筛选和状态展示使用；不新增单独的状态字典接口。

### 互检模板录入参数收敛（2026-09-22）

- 新增检查项大类及子项时，前端只提交大类名称和按展示顺序排列的子检查项名称；不再传递 `categoryKey`、`itemKey` 或 `sortNo`。
- 后端按所属评审类型和新记录 ID 自动生成稳定内部编码；大类追加至该评审类型的末尾，子项按请求数组顺序自动编号。修改已有类别时保留原有内部编码，并按本次子项数组顺序重排子项。
- 删除类别或子检查项统一使用 `DELETE /check-item-templates/<checkItemId>?category=CATEGORY|ITEM`，传检查项 ID 与目标类别；不再传 `templateId` 或 `version`。删除大类会级联逻辑停用本评审类型下的子项，删除子项仅逻辑停用该项。
- 互检单管理页已改为参考原型的模板树布局：默认只显示类别卡片和子检查项列表，顶部提供“新增类别”和“导入 Excel”；编辑类别、编辑/新增子检查项均在对应类别卡片内展开，不使用遮罩弹窗。

### 文件类别收敛（2026-09-22）

- `FileCategory` 统一为六个业务类别：`TASK_CREATION`（任务创建）、`PCB_REVIEW`（PCB评审）、`SCHEMATIC_REVIEW`（原理图评审）、`MUTUAL_CHECK_REVIEW`（互检单评审）、`PROCESS_REVIEW`（工艺评审）、`STRUCTURE_REVIEW`（结构评审）。旧的 `PCB_SCHEMATIC`、`PROCESS`、`STRUCTURE`、`MUTUAL_CHECK_ATTACHMENT` 和 `OPINION_ATTACHMENT` 不再作为文件类别。
- 上传场景仍保持创建、工艺、原理图和互检单四类。工艺/结构图上传统一使用允许的 `PROCESS_REVIEW` 场景，后端根据 `fileKind=PROCESS|STRUCTURE` 分别落为 `PROCESS_REVIEW`、`STRUCTURE_REVIEW` 两种文件类别，并生成独立内部关联键。
- 阶段文件查询、文件下载权限、归档阶段名称及前端“下载最新版本文件”均已同步改用新的文件类别枚举。

### 统一文件接口与资源目录配置（2026-09-22）

- `FileController` 已合并原 `TaskFileController` 的任务文件登记、当前文件查询与受控下载能力，后者不再暴露 REST 接口。
- `POST /files/upload` 不再接收 `dirPath`；前端传 `file`、可选 `taskId` 和必填 `fileCategory`。后端按环境变量 `RESOURCE_SERVICE_DIR_PATH` 读取目录，测试默认 `/user/bms_platform/pcb_review/test1`，`prod` 默认 `/user/bms_platform/pcb_review/pro`，并在目录末尾追加 UUID 后调用公司上传接口。没有 `taskId` 时仅允许 `TASK_CREATION`，元数据写入 `pending_file_upload` 并返回 UUID；有 `taskId` 时立即保存任务、类别、大小、格式、UUID/资源标识、上传时间和当前流程节点。
- 公司资源服务前缀由 `RESOURCE_SERVICE_API_PREFIX` 配置，默认 `http://10.195.135.149:30860/leapmotor/pm/resource`；上传、下载分别调用该前缀下的 `/upload`、`/download`。不再使用 Mock 地址、伪造资源路径或空下载内容；资源服务未配置、调用失败或未返回文件标识时明确返回外部服务异常。 `POST /files/download` 必传 `taskId`、唯一 `fileId`；后端根据文件记录取得类别并进行权限校验，再代理资源服务二进制响应。
