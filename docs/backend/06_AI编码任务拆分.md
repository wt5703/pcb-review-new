# PCB 评审平台 AI 编码任务拆分

## 任务拆分原则

每个任务按一个业务垂直域交付：领域规则、数据库迁移、应用服务、REST 接口、权限校验、审计/事件影响和自动化测试同时完成。后续任务只能依赖已完成任务公开的接口与数据模型。

### 本轮需求补充（2026-09-18）

- 根包及 Maven GroupId 已由 `com.leapmotor.pcbreview` 迁移为 `com.bms`；生产代码、测试、日志配置和后端架构文档已同步。
- `POST /check-item-templates/import` 已支持 `multipart/form-data` 的 Excel 批量导入。首个工作表表头必须依次包含（顺序可调整）`评审类型`、`检查项编码`、`父级检查项编码`、`检查项名称`、`排序号`、`是否启用`；评审类型支持 `PCB`/`SCHEMATIC`，启用值支持 是/否、true/false 或 1/0。任何行校验失败会使整份导入回滚。
- `GET /tasks/{taskId}/opinions` 的每条意见返回 `replies` 历史数组：每一项包含答复轮次、答复结论、答复内容、答复人、答复时间，并内嵌该轮唯一对应的 `confirmation`（确认结论、意见、确认人、确认时间；尚未确认时为 `null`）。不再仅返回最新答复的扁平字段，前端可完整回显多轮答复与确认历史。

### 原理图评审流程工作台适配（进行中，2026-09-20）

- 已将原理图任务详情切换为独立的八步流程：创建、互检分配、互检、设计者答复、硬件专家分配、原理图评审、设计者答复、结束；阶段页签与用户提供的原型一一对应，并保留独立的归档记录页。
- 互检负责人分配会使用 `SCHEMATIC_MUTUAL_CHECK`，硬件专家分配会使用 `SCHEMATIC_HARDWARE_EXPERT`；人员分配成功后，前端调用既有流程接口分别执行 `START_SCHEMATIC_MUTUAL_REVIEW` 或 `START_SCHEMATIC_EXPERT_REVIEW`，不再只是保存人员而没有进入下一阶段。PCB 互检分配同步改为 `PCB_MUTUAL_CHECK` + `START_PCB_MUTUAL_REVIEW`。
- 已新增结束确认检查清单和“确认任务结束”入口，调用既有 `FINISH` 流程动作；后端仍负责校验任务必须已进入结束确认状态、所有处理人已完成、意见已闭环、存在最新设计文件，并在成功后冻结归档。
- 接口复核结论：任务详情使用 `GET /tasks/{taskId}`，人员选择使用当前阶段可分配人员接口，批量互检、意见/答复/确认、流程流转、文件下载和归档接口共同覆盖原型所需的读写数据。原理图状态机目前没有将两次“设计者答复”单独持久化为任务状态，而是通过意见的 `PENDING_REPLY`/`PENDING_CONFIRMATION` 生命周期驱动；页面已按阶段展示。若后续要求这些节点必须作为不可跳过的独立工作流关口，需另行扩展 `TaskStatus` 与流程动作，并补充状态迁移测试。

### 工作台、任务列表与互检单管理页面适配（进行中，2026-09-20）

- 工作台改为统计卡、待处理任务表与流程提醒卡；任务列表和“我的任务”统一任务名称、项目名称、类型、状态、期望完成日期、设计者、评审角色和操作字段的呈现，继续调用既有任务查询与待办接口。
- 创建评审任务页面保持现有字段校验边界和文件多选逻辑，改为从 Mock 用户目录选择设计者、专家/组长；文件由浏览器直接上传公司资源服务，提交仍传用户 ID、冗余姓名及资源服务返回的唯一文件标识，避免页面展示名与服务端权限标识混淆。
- 为支持互检单管理页的真实类别树与操作，`GET /check-item-templates?reviewType=PCB|SCHEMATIC` 返回 `[{ category, items }]`：大类和子项均只含 `id`、`itemName`、`sortNo`，不含 `opinion`、评审类型、内部编码、父级编码、启用状态或版本。删除使用 `DELETE /check-item-templates/<checkItemId>?category=CATEGORY|ITEM`，必须显式声明目标为大类还是小类。大类删除会逻辑停用本评审类型下的全部子项，子项删除只停用该项；类别与记录层级不一致会被拒绝。前端已支持类别树展示、Excel 导入、创建、一次编辑类别及多个子项、逻辑停用。
- 根据互检单管理原型进一步调整：新增类别区固定在页面顶部，直接填写“类别 + 多个检查项”，仅展示业务名称；内部唯一编码在新增时自动生成。下方模板区使用类别卡片、序号、检查项、编辑类别/检查项和删除入口布局；删除按钮仍调用逻辑停用，避免界面文案造成物理删除误解。
- 检查项小类名称编辑收敛为 `PUT /check-item-templates/items/{checkItemId}`：路径仅传检查项 ID，请求体仅传 `itemName`；不要求类别、大类 ID、排序号、内部编码或版本字段。类别编辑仍使用原类别维护接口。
- 修改类别及子项使用 `PUT /check-item-templates`，不再传 `templateId` 或 `reviewType`。`UpdateTemplateRequest` 仅接收 `categoryId`、类别名称和子项列表；子项只传已有项 `itemId`（新增项不传）与 `itemName`。后端根据 `categoryId` 读取类别所属流程，不接收类别或子项的 `enabled`、`version`，并读取保留已有启停状态和版本控制字段。
- 新增检查大项 `POST /check-item-templates` 的 `categoryName` 为必填，`items` 为非必填；可省略或传空数组，后端会只创建大项，后续可再新增对应子项。

### 评审人员白名单（2026-09-22）

- `POST /reviewer-whitelists` 通过 `roleEmployeeNos` 传递职责及多个 `employeeNos`。支持硬件（`HARDWARE_EXPERT`）、EMC（`EMC_EXPERT`）、结构（`STRUCTURE_EXPERT`）、工艺（`PROCESS_EXPERT`）、PCB（`PCB_EXPERT`）评审，以及 PCB 互检（`PCB_MUTUAL_CHECK`）和原理图互检（`SCHEMATIC_MUTUAL_CHECK`）职责；同一职责不得在请求中重复，单个职责下工号不得重复。前端统一读取 `GET /dictionaries/task-options` 的 `reviewerWhitelistRoles`，获得稳定枚举编码及中文名称。
- 新增 `DELETE /reviewer-whitelists?id={id}` 或 `DELETE /reviewer-whitelists?employeeNo={employeeNo}` 逻辑删除白名单：两者必须二选一；按主键仅删除该条角色—工号映射，按员工工号删除该工号全部启用映射。记录不物理删除，后续新增相同角色和工号时会恢复。
- 任务互检单实例 `task_check_item` 不再保存 `templateItemKey`、`parentItemKey`，改用 `parentId` 表达实例父子关系；查询接口按模板物化类别和子检查项，并在每个检查项的 `opinions` 字段返回该检查项关联的互检意见。
- `reviewer_whitelist` 以一行一个“评审角色 + 员工工号”映射保存，唯一约束保证同一映射不会重复落库。接口重复提交既有映射时幂等忽略，并返回本次新增数量及当前白名单映射。

### 创建/保存任务与评审文件引用一体化提交（已完成，2026-09-21）

- `POST /tasks/save` 和 `POST /tasks/submit` 使用 JSON 任务表单；`files` 为多个已上传文件 UUID 的字符串数组。后端从 `review_file` 的待绑定记录读取文件名、大小、格式、MD5 和资源路径，不接收前端文件元数据；同一任务重复传入已关联 UUID 会被拒绝。

- REST 集成测试验证保存/提交请求携带两个文件 UUID 后，任务进入 PCB 待评审状态，且数据库原样登记两条 `file_id`、资源路径与文件元数据。

- `WorkflowAction` 仅保留十个业务动作：`CREATE`、`START_PCB_STRUCTURE_REVIEW`、`START_PCB_PROCESS_REVIEW`、`START_PCB_MATUAL_ASSIGNMENT`、`START_PCB_MATUAL_REVIEW`、`START_SCHEMATIC_MATUAL_REVIEW`、`START_SCHEMATIC_EXPERT_ASSIGNMENT`、`START_SCHEMATIC_EXPERT_REVIEW`、`PREPARE_FINISH`、`FINISH`。`CREATE` 是任务提交职责：`POST /tasks/submit` 创建 PCB 任务后直接进入专家评审，创建原理图任务后直接进入互检单分配；`transition` 收到 `CREATE` 会明确拒绝，避免将创建与既有任务的状态推进混用。
- PCB 流程顺序为：创建后专家评审；设计者上传工艺、结构文件后，同次以 `START_PCB_STRUCTURE_REVIEW`、`START_PCB_PROCESS_REVIEW` 开启结构、工艺评审；全部前序意见闭环后，设计者分别上传最新工艺、结构文件，并以 `START_PCB_MATUAL_ASSIGNMENT` 进入互检单分配；PCB 组长以 `START_PCB_MATUAL_REVIEW` 携带 `PCB_MUTUAL_CHECK` 及 `reviewerIds` 分配并开启互检；互检意见闭环后由设计者执行 `PREPARE_FINISH`，最后由 PCB 组长 `FINISH`。

- 准入条件按意见来源精确校验：开启 PCB 工艺或结构评审前仅要求 `EXPERT_REVIEW` 全部确认通过（或撤回）；开启 PCB 互检单分配前要求专家、工艺和结构意见全部确认通过（或撤回）；开启原理图专家分配前要求互检单意见全部确认通过（或撤回）；结束任一任务前要求该任务的全部意见确认通过（或撤回）。不再将“评审人无意见提交”或“所有处理人已提交”作为额外的流程动作或硬性流转条件。
- `PREPARE_FINISH` 也按流程类型校验：PCB 必须全部互检单意见通过，原理图必须全部原理图专家评审意见通过；该动作仅任务设计者可执行。进入待结束节点后，`FINISH` 由 PCB/原理图组长执行，并再统一校验该任务全部历史意见均已确认通过或撤回。

- `transition` 请求使用 `actions` 数组而非单个 `action`：PCB 设计者同时开启工艺、结构评审时传 `actions=["START_PCB_STRUCTURE_REVIEW","START_PCB_PROCESS_REVIEW"]`，服务在同一事务内依次完成两个动作；其他场景 `actions` 必须只含一个动作。该请求不再接收 `stageFiles`，也不再存在 `FileUploadScene`：设计者应先调用文件域 `POST /files/upload`（携带 `taskId` 与 `FileCategory`）登记文件信息，再提交对应动作，流程服务只校验最新文件是否已经存在。

- 每个 Sheet 的列为序号、评审阶段、位置、问题描述、提出人、严重等级、处理情况、提出人确认。位置来自 `richText` 并转换为可阅读文本；每轮设计者答复各占一行，显示答复类型/说明和对应专家确认结果；尚无答复的意见保留“待设计者答复、待专家确认”。
- 导出单测以 EMC 与结构评审为例，校验角色 Sheet 拆分、富文本中的换行/图片占位、同一意见的两轮答复展开及专家确认结果的写入。

### 业务评审角色与流程分配职责解耦（2026-09-29）

- `ReviewRole` 现在只表达任务业务评审角色，并固定为 `HARDWARE_EXPERT`（硬件评审）、`EMC_EXPERT`（EMC评审）、`PCB_EXPERT`（PCB评审）、`PROCESS_EXPERT`（工艺评审）、`STRUCTURE_EXPERT`（结构评审）。枚举自带 `displayName`，不再引用或持有任何 `Permission`。
- 新增 `WorkflowAssignmentRole` 承担流程节点中的人员分配职责与权限映射：PCB/原理图互检单分配、原理图硬件专家分配均由该枚举校验对应的 `Permission`。`WorkflowController#transition` 的 `assignedRole` 改为该枚举，避免把流程职责误当作业务评审角色。
- 新增 `ReviewerWhitelistRole` 管理白名单的七种可配置类别：五种业务评审角色加 PCB/原理图互检单评审。它可将五种业务类别映射回 `ReviewRole`，而互检单类别保持独立；白名单管理接口、字典和任务创建时的白名单校验均使用这一边界。
- 原理图专家评审的未提交统计继续使用任务创建时保存的硬件、EMC、PCB 三种业务角色；互检单人员属于流程分配，不会再被错误写入或读取为 `ReviewRole`。归档 Excel 对没有历史角色映射的专家意见使用“专家评审”Sheet 兜底，不再依赖已移除的枚举值。

### 草稿任务文件重复提交幂等处理（2026-09-29）

- 编辑草稿时，前端可以在 `files` 中同时提交本次新上传的文件 UUID 和已经绑定到当前任务、用于页面回显的旧 UUID。`FileApplicationService#bindPendingInitialFiles` 对已绑定到当前任务的文件直接返回已有记录，不重复更新、不重复生成关联。
- 文件 UUID 已绑定到其他任务时仍会拒绝，防止跨任务复用；同一次请求内重复传同一个 UUID 仍视为前端参数错误。任务文件 ID 聚合沿用领域对象的去重逻辑，因此后续保存或提交不会把同一文件写入 `initial_file_ids` 两次。

### 任务详情流程记录（2026-09-29）

- `GET /tasks/{taskId}` 不再返回邮件通知投递记录；邮件属于通知域，避免在任务详情响应中暴露收件人、投递状态等无关信息。
- 任务详情新增 `flowRecords`，数据直接来自 `task_flow_record` 并按记录 ID（即操作顺序）返回。每条记录包含操作动作编码、中文动作名称、操作人 ID/姓名、操作说明和操作时间；操作人账号已停用或缺失时以“用户#ID”兜底。
- 任务详情“任务信息”页新增流转记录表，实时显示任务创建及后续流程推进的操作人、动作、时间和说明；任务结束后归档页仍展示同一来源的冻结流程视图。

### 归档流程、邮件记录快照（2026-09-29）

- `TaskArchiveApplicationService#archive` 在任务结束事务中除冻结最新阶段文件外，会查询 `task_flow_record` 并将节点时间、动作中文名称、操作人和说明序列化到 `task_archive_snapshot.flow_snapshot`。归档后读取流程记录不再重新查询实时流程表。
- `task_archive_snapshot` 同时保存阶段文件、`flow_snapshot` 和 `notification_snapshot`。任务详情接口不返回邮件，但 `GET /tasks/{taskId}/archive` 返回归档时冻结的邮件投递记录，供追溯收件人、模板、投递状态、失败原因和尝试时间。
- Flyway 增量脚本会为已有数据库补齐 `flow_snapshot` 和 `notification_snapshot` 字段；全新数据库同样会在建表和初始化后自动执行该增量迁移。

### 任务访问 Mapper 归属调整（2026-09-29）

- `TaskAssignmentAccessMapper` 已从 `com.bms.identity.infrastructure` 移至 `com.bms.task.infrastructure`。该 Mapper 查询 `review_task` 的设计者、组长和已分配人员，是任务域数据访问职责，不再放在身份域。
- 身份授权服务、文件域、评审域和任务域中引用该 Mapper 的代码及相关单测已统一切换到新包名，SQL 与原有可见性、当前处理人校验逻辑不变。

### 我的待办仅查询未结束任务（2026-09-29）

- `MyTaskApplicationService#list` 改为调用 `ReviewTaskMapper#findAllUnfinished`，SQL 在数据库侧使用 `status <> 'FINISHED'` 限定任务范围。应用层不再先遍历全部任务后再生成待办。
- 待答复、待确认、评审、人员分配和结束动作仍在未结束任务集合中计算，返回字段和既有权限判断保持不变。

### 任务列表统一请求体查询（2026-09-29）

- 任务列表接口由 `GET /tasks` 调整为 `POST /tasks/query`。所有筛选字段和分页参数统一放在 `TaskListQueryRequest` 请求体中，避免使用数量过多的 `@RequestParam`。
- 请求体支持 `taskName`、`projectName`、`designerName`、`reviewType`、`status`、`pageNo`、`pageSize`，均为可选；未传分页参数仍按第 1 页、每页 20 条执行。前端任务列表已改为 POST JSON 调用。

### 接口人员标识统一使用工号（2026-09-29）

- 前端不再传递 PCB 系统内部用户 ID。当前登录身份由后端统一获取；任务创建、草稿编辑和流程人员分配中的被选人员统一提交 `employeeNo` 或 `reviewerEmployeeNos`。
- `MockUserDirectoryApplicationService` 是本地联调时的企业人员目录适配层：它按工号查询被选择的白名单人员，并只在后端将工号转换为内部关联 ID。生产环境可替换该目录适配层，而不需要修改任务或工作流接口。
- `POST /tasks/save`、`POST /tasks/submit` 的设计者由当前登录工号确定，不再接受 `designerId`、`designerName`；原理图组长改为 `expertLeaderEmployeeNo`；每个业务评审角色的人员字段改为 `reviewerEmployeeNos`。
- `POST /tasks/{taskId}/workflow/transitions` 的分配人员字段改为 `reviewerEmployeeNos`。可分配人员列表仍返回工号供页面展示和提交，内部 `userId` 仅保留给后端关联和既有响应兼容。

### 当前用户改由用户中心获取（2026-09-29）

- 所有业务接口的当前用户均由请求过滤器调用 `UserCenterCurrentUserClient` 获取，控制器和前端不再传递或解析用户 ID、员工工号、角色等身份字段。前端请求仅携带常规认证信息（例如后续由网关注入的 Authorization），不再伪造身份请求头。
- 用户中心地址使用 `user-center.current-user-url`（环境变量 `USER_CENTER_CURRENT_USER_URL`）配置。适配器会转发当前请求的 `Authorization` 头，并约定用户中心返回 `userId`、`employeeNo`、`displayName`、`roles`；用户中心实际接口联通后只需配置地址或按真实响应调整适配器。
- 当前接口尚未联通或调用失败时，适配器统一回退为默认 Mock 用户“王鹏飞”（内部关联 ID 为 1，拥有全部系统角色），保证本地流程可继续联调。前端顶部也明确标记“王鹏飞（用户中心 Mock）”，不再提供会误导后端身份的本地用户/角色切换。
- 默认 Mock 用户具有硬件开发部经理角色，因此可以处理其他用户预上传、但尚未绑定任务的文件；该管理员例外与“王鹏飞可以执行所有操作”的联调约定一致，普通用户仍只能绑定自己上传的文件。

### 白名单成为唯一的本地人员目录（2026-09-29）

- PCB 系统不再维护本地 `user_account`、`user_role`，也不再保留 `role_definition`。登录身份、组织岗位和权限由用户中心提供；PCB 本地仅维护业务所需的评审/互检单白名单。
- `reviewer_whitelist` 增加并直接保存 `display_name`、`email`、`mobile`、`department_name`。白名单管理、任务创建的角色人员下拉、流程分配、邮件收件人和工号解析都只读取该表，不再关联本地用户表或调用 Mock 用户目录接口。
- 新增 Flyway `V4__remove_local_user_tables.sql`：先把旧用户角色中仍属于七种白名单类别的人员资料迁入白名单，并为本地初始化的评审、互检人员补齐默认白名单，再补全已有白名单的人员资料，最后删除旧三张表。设计者、组长、管理员等非白名单身份不迁入，因为它们已改由用户中心识别。
- 迁移不改写既有 V1/V2 历史脚本，已部署数据库可直接执行新增 V4；全新数据库在 V4 完成后同样只保留白名单人员目录。一个人员可属于多个白名单类别，任务创建和流程分配按“类别 + 工号”精确解析白名单记录，避免错误取到该人员的另一种角色记录。

### 白名单分页与关键字查询（2026-09-29）

- 白名单列表调整为 `POST /reviewer-whitelists/query`，请求体使用一个查询字段 `keyword`，同时对 `employeeNo`（工号）和 `displayName`（姓名）做模糊匹配；`pageNo` 默认 1，`pageSize` 默认 20、最大 1000。
- 响应统一为 `total`、`pageNo`、`pageSize`、`items`，管理页新增工号/姓名搜索框、总数和上一页/下一页控制。创建任务和任务详情为保持角色人员解析完整性，会以最大页大小读取白名单候选数据。
- 集成测试覆盖按工号和按姓名的两种关键字查询，确认分页记录和总数均正确返回。

### 互检检查大类移除冗余评审类型（2026-09-29）

### 每类评审唯一互检单模板（2026-09-29）

- PCB 和原理图各自只维护一套互检单模板；`check_item_template` 中同一 `review_type` 的全部大类和子项共同组成该唯一模板，不再提供模板 ID 的选择或混合两种类型模板的读取方式。
- `GET /check-item-templates` 的 `reviewType` 改为必传，只能读取 PCB 或 SCHEMATIC 的对应模板。模板管理页始终按当前选中的任务类型调用该接口。
- `TaskCheckItemApplicationService#list` 和原先的 `synchronizeIfActive` 统一为“按任务类型生成唯一模板快照”的语义：当前任务只从自身 PCB/原理图类型的模板读取检查项，互检单中不会混入另一类型的模板数据。
- Excel 导入不再作为模板的增量更新方式。导入前会查询当前 PCB 或原理图类型是否已有启用模板；存在任一大类或子项即返回 `DUPLICATE_REQUEST` 和“互检单模板已存在，不能重复导入”提示，原模板不会被覆盖。只有逻辑停用全部旧记录后，才允许重新导入一套新模板。

### 互检检查项提交不再同步模板（2026-09-29）

- 单项提交 `submit` 和批量提交 `submitBatch` 不再调用模板同步逻辑。它们只定位 `task_check_item` 中已经物化的任务检查项快照，避免模板管理人员的修改在评审人员保存结论时意外改变当前互检单。
- 两个提交流程均明确分为：校验任务状态和节点权限、校验任务快照归属与提交内容、根据合格/不合格结论处理同源互检意见、写入检查项结论和图文说明。批量操作任一项失败时由事务整体回滚。
- 单测覆盖单项及批量提交均不会调用 `findEnabledByReviewType`，确保保存路径不再读取或生成模板数据。

### 导入互检单模板前确认替换（2026-09-29）

- 新增 `GET /check-item-templates/existence?reviewType=PCB|SCHEMATIC`，返回当前类型是否存在启用模板及其大类、子项数量。页面选中 Excel 后先调用该接口；存在模板时明确提示用户确认。
- `POST /check-item-templates/import` 新增 multipart 参数 `confirmed`，默认 `false`。已有模板且未确认时返回“请确认后重新导入”；确认后才逻辑停用旧模板并在同一事务中导入新模板。已创建任务使用任务检查项快照，不受模板替换影响。

### 评审意见内容统一为 comment（2026-09-29）

- `OpinionController` 的提出、编辑意见请求及意见返回模型统一使用 `comment` 表示问题描述；`richText` 仍用于保存完整图文内容。前端接口与互检额外意见调用同步改为传递和读取 `comment`。
- `review_opinion.content` 重命名为 `review_opinion.comment`：`V5__rename_review_opinion_content_to_comment.sql` 会在新环境初始化及已有数据库升级时保留历史数据完成迁移；既有 `V1__ddl.sql` 不改动，避免已部署环境出现 Flyway 校验和不一致。
- 互检固定项关联意见、归档意见导出及相关持久化映射同步使用 `comment`。任务流程记录、邮件正文和文件二进制等非评审意见的 `content` 字段不受影响。

### 任务列表使用 URL 参数和统一关键字（2026-09-30）

- `TaskController#list` 改回 `GET /tasks`，不再使用 `TaskListQueryRequest` 请求体。筛选条件通过 `keyword`、`reviewType`、`statuses`、`pageNo`、`pageSize` 等 URL 参数传递。
- `keyword` 同时模糊匹配任务名称、项目名称和设计者名称，列表页面也收敛为一个“项目名称、任务名称或设计者名称”输入框；状态仍可多选。
