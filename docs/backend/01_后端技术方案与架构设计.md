# PCB 评审平台后端技术方案与架构设计

## 1. 定位与依据

本文是后端实现方案，不新增 PRD 之外的业务规则。业务含义、角色、状态、权限和验收条件以 `PCB评审平台_PRD.md` 为准；本文只定义其在 Java 后端中的分层、调用、可靠性与工程约束。

当前工程已确定：Java 17、Maven、根包 `com.bms`。以下组件为推荐基线，开始编码前应在项目中确认：Spring Boot 3.x、Spring MVC、Spring Validation、Spring Security、MyBatis/MyBatis-Plus、MySQL 8、Flyway、Redis、OpenAPI。

## 2. 架构原则

1. 模块化单体优先。首期以单个 Spring Boot 应用部署，模块边界清晰，不提前拆微服务。
2. 分层依赖方向固定：`interfaces → application → domain → infrastructure`。领域层不得依赖 Web、ORM 或邮件 SDK。
3. 业务写操作由应用服务编排事务；领域对象/领域服务承载规则；基础设施实现数据库、文件、邮件、身份等适配。
4. 所有跨模块异步副作用通过领域事件和 Outbox 处理，避免事务内直接发送邮件。
5. 权限、状态、对象归属在后端强制校验，前端不作为安全边界。

## 3. 推荐模块结构

```text
com.bms
├─ common                 # 统一响应、异常、错误码、时间、分页、ID
├─ task                   # 评审任务域
├─ review                 # 评审域：人员关系、互检、意见与闭环
├─ file                   # 文件与版本域、CompanyFileClient
├─ identity               # 当前用户、角色、数据范围、授权服务
├─ workflow               # 状态准入和流程推进
├─ notification           # 事件、Outbox、邮件发送与重试
├─ audit                  # 操作审计、任务归档快照
└─ interfaces             # REST Controller、DTO、全局异常处理
```

每个业务模块内部采用：

```text
{module}/
├─ domain         # 聚合、值对象、枚举、领域服务、仓储接口
├─ application    # Command/Query、应用服务、事务边界、事件发布
├─ infrastructure # Mapper、DO、仓储实现、外部客户端
└─ interfaces     # Controller、Request/Response DTO
```

禁止建立独立“评审执行域”或“评审单”模块。任务与评审人员的处理关系属于 `review` 模块内部模型。

## 4. 关键调用关系

```text
REST Controller
  → Application Service（认证用户、参数、事务、用例编排）
    → Authorization Service（角色 + 数据范围 + 当前节点）
    → Domain/Repository（规则、持久化）
    → Outbox（同事务保存业务事件）
异步 Outbox Worker
  → Notification Service → Mail Client → 发送记录/重试
```

流程推进由 `workflow` 计算当前任务是否满足准入条件，并调用任务应用服务提交状态转换。`workflow` 不得直接 SQL 更新意见、文件或人员处理关系。

## 5. 事务、一致性与并发

| 场景 | 实现要求 |
| --- | --- |
| 创建/提交任务 | 任务、初始文件关联、审计记录、Outbox 事件同事务提交 |
| 分配/改派人员 | 人员处理关系和审计同事务提交；历史记录不可覆盖 |
| 提交意见/答复/确认 | 状态校验、处理记录、审计同事务提交 |
| 状态推进/结束任务 | 当前状态、全部完成条件、意见状态、最新文件条件在事务内校验 |
| 邮件通知 | Outbox 异步发送；邮件失败不回滚业务事务 |

任务、意见、人员处理关系使用乐观锁 `version` 字段。更新语句必须带版本条件；并发失败返回统一的“数据已更新，请刷新后重试”业务错误。写接口支持 `Idempotency-Key`，重复请求只返回第一次成功结果。

## 6. 外部适配

| 能力 | 抽象接口 | 实现约束 |
| --- | --- | --- |
| 公司身份服务 | `IdentityClient` | 只向领域暴露当前用户和角色/组织信息 |
| 文件服务 | `CompanyFileClient` | 上传、下载、预览 URL、文件删除/状态查询；不把 SDK 暴露给业务层 |
| 邮件服务 | `MailClient` | 由通知模块调用；支持幂等发送标识和失败原因 |
| 缓存 | `CachePort`（可选） | 缓存不得作为权限、流程或审计的唯一事实来源 |

外部客户端要配置连接/读取超时、重试边界、熔断或降级策略，并记录关联任务 ID 与追踪 ID。外部失败的可见错误不得泄露凭据或内部响应。

## 7. 横切规范

- API 统一前缀为 `/leapmotor/pcb_review`；日期使用 ISO-8601 且保存 UTC 时间。
- 所有请求生成/透传 `traceId`；日志包含 traceId、用户 ID、任务 ID（如有），不得包含令牌、密码或文件内容。
- 统一异常映射：参数错误、未认证、无权限、资源不存在、状态冲突、并发冲突、外部依赖失败。
- Flyway 管理全部 schema 变更；禁止应用启动时自动修改生产表结构。
- OpenAPI 由 Controller/DTO 注解或契约文件生成，并纳入 CI 校验。

## 8. 工程落地顺序

1. 建立 Spring Boot 基础骨架、配置分层、统一响应/异常、测试基础设施。
2. 建立数据库迁移、身份上下文、权限拦截器、审计基础能力。
3. 实现任务、当前文件、评审人员关系、意见闭环。
4. 实现流程编排和任务结束条件。
5. 接入 Outbox 与邮件、文件服务适配。
6. 补齐接口契约、集成测试、监控与部署配置。
