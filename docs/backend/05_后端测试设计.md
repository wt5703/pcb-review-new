# PCB 评审平台后端测试设计

## 1. 目标与工具建议

测试以 PRD 验收为唯一业务依据，遵循“先失败、后实现”。建议使用 JUnit 5、AssertJ、Spring Boot Test、Testcontainers（MySQL/Redis）和 MockWebServer/WireMock（外部服务）；最终工具以工程依赖确认结果为准。

测试金字塔：领域规则以单元测试为主，应用服务以集成测试验证事务与权限，REST 接口验证序列化和安全链路；外部文件/邮件服务使用可控 mock 或容器替身。

## 2. 测试分层

| 层级 | 范围 | 要求 |
| --- | --- | --- |
| 单元测试 | 状态/完成条件、意见状态、权限策略、MD5 与版本规则 | 快速、无网络、无真实数据库 |
| 仓储测试 | Mapper、索引关键查询、数据范围过滤 | 使用真实兼容数据库 |
| 应用服务测试 | 事务、审计、Outbox、幂等、乐观锁 | 启动最小 Spring 上下文 |
| API 集成测试 | 认证、DTO 校验、错误码、分页、授权 | 通过 HTTP 层调用 |
| 外部适配测试 | 文件/邮件/身份协议、超时、失败、重试 | Mock server 或契约测试 |

## 3. 必须覆盖的测试场景

### 3.1 任务与流程

- 创建草稿允许 PRD 允许缺失字段；提交缺少必填字段必须失败。
- 非法任务状态转换失败，响应 `TASK_STATUS_CONFLICT`。
- 同一角色多人时，只要有一人未提交或其意见未闭环，阶段不得推进。
- 所有必需人员提交且相关意见闭环/无意见后，允许推进。
- 结束前缺少最新设计文件、未完成角色或未闭环意见时必须失败。
- 已结束任务不能新增意见、答复、分配、文件关联或再次结束。

### 3.2 评审与意见

- 提出意见后为待答复；合法答复后为待确认；确认通过关闭；确认不通过回到待答复。
- 非提出人确认意见失败；非设计者/无答复权限者答复失败。
- 设计者上传新版本并关联答复后，只允许该意见进入确认，不创建或重置其他已完成评审人的处理关系。
- 提交无意见会标记人员完成，但不会产生意见数据。
- 固定检查项不合格时，未关联意见且无豁免说明不得提交。

### 3.3 权限与数据范围

- 每个写接口至少覆盖：合法处理人成功、只有查看权失败、无功能权限失败、跨任务 ID 越权失败。
- 工艺、结构专家不能查询超出授权范围任务；其他角色按 PRD 全量可见规则验证。
- EMC 专家可以获取 PCB/原理图下载 URL；无下载权限用户被拒绝。
- “我的任务”只包含当前节点要本人处理的记录，不包含仅可查看、已完成、已结束或等待他人的任务。

### 3.4 文件、通知、审计与并发

- 相同 MD5 不重复创建文件版本；同一版本链只有一个最新版本。
- 文件 ID 与任务不匹配时上传关联/下载失败。
- 业务提交成功时 Outbox 与审计同事务存在；事务失败时三者均不落库。
- 重复消费同一 Outbox 事件不重复发送同一收件人邮件。
- 邮件服务失败时记录失败并可重试，业务任务状态不回滚。
- 两个并发确认/结束请求只允许一个成功，另一个返回 `VERSION_CONFLICT` 或状态冲突。

## 4. 测试数据与隔离

1. 每个测试独立创建数据，不依赖执行顺序或共享测试账号。
2. 测试名称使用“条件—动作—结果”形式，例如 `全部互检人提交且意见闭环时_进入专家评审成功`。
3. 测试身份通过可控 Security Context 构造，不调用真实公司身份服务。
4. 用固定时钟和固定 ID 生成器替代真实时间/随机数，确保断言稳定。
5. 集成测试使用临时数据库或容器，测试结束后清理；禁止连生产/共享环境。

## 5. CI 质量门禁

每个合并请求至少执行：编译、格式化检查、静态分析、单元测试、仓储/应用服务测试、API 集成测试和依赖漏洞扫描。覆盖率只作为质量信号，不能替代关键路径断言；新增状态、权限、事务或外部事件逻辑必须有针对性测试。

缺陷修复的固定流程：先新增能失败且可复现缺陷的回归测试，再修复代码；禁止只修改生产代码后声称问题已解决。
