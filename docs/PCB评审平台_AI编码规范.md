# PCB 评审平台 AI 编码规范

| 项目 | 内容 |
| --- | --- |
| 版本 | V2.0 |
| 适用对象 | 参与本项目编码、测试、排障和代码审查的 AI |
| 业务需求来源 | `PCB评审平台_PRD.md` 及用户当次确认的需求 |

## 1. 文档定位

本规范不定义业务流程、角色权限、状态、字段、页面或接口的业务含义。

这些内容只能由 PRD、已确认需求、接口契约和用户当次指令定义。本规范只规定 AI 在实现需求时必须遵守的工作方式、质量底线和交付要求。

规则优先级如下：

`用户当次明确指令 > 已确认 PRD/需求文档 > 项目既有约定 > 本规范 > AI 技术偏好`

## 2. AI 的职责边界

AI 可以：

- 阅读需求、代码、测试、配置和已有文档，定位实现位置。
- 将已确认的需求实现为代码、测试、迁移和必要的接口变更。
- 发现需求与代码、测试或文档的矛盾并提出问题。
- 在不改变业务含义的前提下，作出最小化的技术实现选择。

AI 不可以：

- 自行设计或修改业务规则、流程、权限、状态机、字段含义、角色或通知场景。
- 因实现复杂而删除、简化或绕过已确认需求。
- 将推测写成既定规则，或把未确认的假设写入代码、数据库或文档。
- 擅自扩大改动范围、引入大型依赖、重构无关模块或修改无关配置。
- 通过关闭测试、放宽鉴权、吞掉异常或删除校验来使功能“看起来可用”。

## 3. 每次编码的标准流程

### 3.1 开始前

1. 阅读当前需求对应的 PRD 章节，以及相关源码、测试、接口定义和项目约定文件。
2. 简要说明：要修改什么、影响哪些模块、影响哪些已有接口或数据、如何验收。
3. 检查工作区已有改动，避免覆盖用户或其他任务的未提交内容。
4. 仅在确有必要时创建技术计划；简单任务可直接进入测试设计。

### 3.2 需求不明确时

以下情况必须暂停业务实现并向用户提问：

- PRD 和用户最新指令结论冲突。
- 需求没有定义必要的业务结果、权限口径、数据归属、失败处理或边界条件。
- 需要新增业务状态、字段、接口语义、角色、流程或外部集成。
- 修改可能影响历史数据、已上线接口兼容性、数据迁移或安全边界。

提问必须简洁说明冲突点、受影响范围和最小需要确认的问题。若用户明确要求不中断开发，AI 应采用可替换的本地 Mock、接口抽象或技术默认值继续实现，并在最终交付时汇总待确定项与阻塞项；不得将技术默认值伪装为已确认业务规则。

### 3.3 测试先行

所有业务行为变更必须遵循测试先行：

1. 从需求写出可验证的验收条件。
2. 先新增或修改测试，使其在未实现时失败。
3. 编写最小实现使测试通过。
4. 运行新增测试和相关回归测试。
5. 如需重构，必须在测试全部通过后进行，并再次运行测试。

测试必须验证真实结果，不能只断言 HTTP 状态码、函数未抛异常或 mock 被调用。测试应至少覆盖正常路径、输入校验失败、权限失败、状态/数据冲突和重复请求等与当前变更有关的路径。

## 4. 实现约束

### 4.1 最小改动

- 只修改完成当前需求所必需的文件。
- 复用已有架构、命名、异常、日志、鉴权、事务和依赖管理方式。
- 不因局部需求顺手格式化、重命名、迁移或重构无关代码。
- 需要修改公共接口、公共模型或数据库结构时，先评估所有调用方和兼容性。

### 4.2 后端与数据

- 关键业务校验必须在后端执行；前端控制不能替代后端鉴权或状态校验。
- 写操作应由明确的应用服务或领域服务负责，避免在控制器、路由或 UI 中分散核心规则。
- 修改多份业务数据时使用项目既有事务机制，避免部分成功。
- 对可能重复提交的写操作使用既有幂等方案或明确的唯一约束。
- 数据库迁移必须与实体、查询、测试和回滚/修复方案同步考虑；不得丢弃历史数据。
- 涉及并发更新时使用项目既有的并发控制方式，不能静默覆盖他人最新修改。

### 4.3 API 与前端

- 保持接口命名、请求/响应结构、错误码和分页方式的一致性。
- 不通过万能更新接口绕开已有校验和审计链路。
- 前端仅调用已授权接口并正确展示加载、空态、失败和无权限状态。
- 不在前端硬编码角色、用户 ID、密钥、文件地址或服务端业务规则。

### 4.4 安全与可观测性

- 校验所有外部输入的格式、长度、类型和对象归属。
- 不信任客户端传入的身份、权限、资源 ID、状态或文件信息。
- 不记录密码、令牌、密钥、敏感文件内容或其他不应暴露的数据。
- 发生错误时返回可定位、面向用户的错误信息；不得暴露堆栈、SQL、内部路径或敏感数据。
- 对关键写操作沿用项目审计和日志机制；不得绕过既有审计链路。

## 5. 测试要求

| 测试类型 | 目标 |
| --- | --- |
| 单元测试 | 验证单个规则、计算、校验和异常分支 |
| 接口/集成测试 | 验证鉴权、事务、持久化、序列化和模块协作 |
| 回归测试 | 确认本次修改未破坏相邻能力 |
| 并发/幂等测试 | 当需求涉及状态、分配、确认、上传或重试时验证重复与竞争请求 |
| 前端测试 | 验证用户可见交互、加载/错误状态和关键权限显示；按项目测试栈执行 |

测试数据必须独立、可重复执行且易读。发现缺陷时，先增加可复现问题的回归测试，再修改实现。

禁止：删除或跳过失败测试、降低断言强度、扩大 mock 范围掩盖问题、仅更新快照而不理解差异。

## 6. 代码质量要求

- 遵守仓库现有的格式化、静态检查、命名、目录和模块边界。
- 新增代码应小而清晰，函数和类只承担一个稳定职责。
- 避免重复逻辑；优先复用已存在且语义相同的能力。
- 注释解释原因、限制或非直观取舍，不复述代码表面含义。
- 每个 Java 源文件须在 import 区结束后、类型声明或第一个类型注解之前添加 Javadoc：`@author 王涛`、`@date YYYY-MM-DD` 和中文的 `@description`。创建日期从当月 9、10、11、14、15、16、18 日中按模块依赖顺序选择；新增或修改类型时必须同步维护该信息。
- 不保留空实现、空 catch、无说明的 `TODO`、死代码、调试输出或临时绕过逻辑。
- 新增依赖前先确认项目内没有等效能力；依赖必须有明确必要性和许可/安全风险评估。

## 7. 完成前检查清单

交付前，AI 必须确认：

- [ ] 已阅读并遵守相关 PRD/需求，没有自行设计业务规则。
- [ ] 变更范围最小，未覆盖无关已有改动。
- [ ] 已先写或更新测试，并覆盖本次需求的关键成功与失败路径。
- [ ] 新增测试、受影响回归测试、构建、格式化和静态检查均已运行并通过。
- [ ] 后端校验、鉴权、事务、错误处理和日志/审计未被绕过。
- [ ] 接口、数据模型、迁移、前端调用和测试保持一致。
- [ ] 未引入硬编码凭据、越权风险、未处理异常或不必要依赖。
- [ ] 已明确说明未运行的检查、已知限制和需要用户确认的事项。

## 8. 交付说明格式

每次完成代码任务时，交付说明应包含：

1. 完成结果：实现了什么，关联哪项已确认需求。
2. 修改内容：按文件或模块概述实际变更。
3. 验证结果：执行了哪些测试、构建、静态检查及其结果。
4. 风险与待确认项：仅列出仍会影响后续实现的事实，不重复无关信息。

## 9. 可复用任务提示词

> 请严格遵守 `PCB评审平台_PRD.md` 和 `PCB评审平台_AI编码规范.md`。不要自行设计业务规则；需求未定义或与现有文档冲突时，先说明问题并等待确认。先阅读相关代码和测试，说明影响范围与验收条件，先写失败测试，再做最小实现。完成后运行相关测试、构建、格式化和静态检查，并报告实际变更、验证结果及待确认事项。
