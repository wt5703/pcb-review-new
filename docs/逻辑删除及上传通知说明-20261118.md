# 逻辑删除及上传通知调整

## 数据库及逻辑删除

14 张业务表统一增加 `delete_status TINYINT NOT NULL DEFAULT 0`：`0` 未删除，`1` 已删除。

- 任务删除保留任务及所有关联数据，将任务、意见、答复、确认、评审完成记录、互检实例、文件记录、流程日志、Outbox、通知记录、归档快照标记为删除。
- 普通查询及更新只处理 `delete_status=0`。删除操作带有 `delete_status=0` 条件，重复删除不会再次更新已删除行。普通业务更新不写入或重置此字段。
- 白名单人员及角色是恢复规则的例外：重新添加时允许原记录从 `1` 恢复为 `0`，保留原 ID。应用统一使用 `delete_status`；旧 `deleted` 列保留用于历史兼容，升级脚本负责迁移其原状态。
- 评审完成记录和未填写互检快照在删除后需要再次新增，唯一约束只约束有效记录，旧记录保留，不从 `1` 恢复到 `0`。
- 互检模板的业务查询排除已删除模板。已有任务的历史快照仍可只读获取原模板名称、说明，以保留已填写的互检结果；重新导入导致的旧版本停用与删除分别处理。

全新数据库使用更新后的 [ddl.sql](database/ddl.sql)。增量变更统一放在 [upgrade.sql](database/upgrade.sql)，涵盖流程字段、评审完成记录与逻辑删除。已有数据库应根据当前表结构执行尚未应用的语句；已执行旧版升级脚本或已使用新版 DDL 建库时，不要重复建表、添加字段或索引。

## 工艺、结构评审邮件

开启 `START_PCB_PROCESS_REVIEW`、`START_PCB_STRUCTURE_REVIEW` 或同时开启二者时，不发送工艺/结构评审邮件。

`POST /files/upload/grouped` 使用 `multipart/form-data`，新增可选参数 `sendMail`；`POST /files/upload/batch` 保持原参数和上传行为，不发送邮件。

| 参数 | 类型 | 说明 |
| --- | --- | --- |
| `taskId` | long | 当前任务 ID |
| `fileCategories` | FileCategory 列表 | 本次上传的多个文件类型 |
| 各 FileCategory 编码 | 多文件 | 文件字段名使用对应类型，例如 `PCB_PROCESS_REVIEW`、`PCB_STRUCTURE_REVIEW`；同一类型可重复多个文件 |
| `sendMail` | boolean | 默认 `false`；传 `true` 才发送对应类型的开启评审邮件 |

发送邮件要求任务处于 PCB 工艺/结构评审阶段，且本次分组包含 `PCB_PROCESS_REVIEW` 或 `PCB_STRUCTURE_REVIEW`。只有所有分组的文件均上传、落库成功后才登记一封邮件 Outbox；同时上传工艺和结构文件时合并通知。附件包含本次涉及的工艺/结构类型的最新批次文件，其他类型的文件正常上传，不进入此评审邮件的附件。分组上传未传 `sendMail` 或传 `false` 时不发邮件；单文件及原批量上传接口不发邮件。

## 验证

`mvn package`：247 项测试通过，失败、错误、跳过均为 0；JAR 和 tar.gz 构建成功。覆盖旧结构迁移、14 张表的默认值、关联数据保留及查询隐藏、重复删除、白名单恢复原记录、重新提交、模板历史读取，以及分组通知开关、多类型合并邮件、后续分组上传失败和原批量上传不发邮件。数据库测试使用 H2 MySQL 兼容模式，未连接线上数据库或发送真实邮件。
